EASYWAY API — TRIPS MODULE — FRONTEND INTEGRATION REFERENCE
Covers: route calculation, trip lifecycle (create/list/detail/update/delete),
rating, and GPS telemetry ingestion. Written against the code as of this
session — verify against /api/docs/ (Swagger, generated from the same code)
if this drifts over time.

Base path: /api/  (all paths below are relative to that)
Content-Type: application/json for every request below
Auth header (ALL endpoints in this file require it):
  Authorization: Bearer <access>
See AUTH_API_FRONTEND.txt for how to get that token.

------------------------------------------------------------
READ THIS FIRST — the shape of the whole flow

  1. POST routes/calculate/          -> up to 3 unsaved route candidates
  2. (user picks one, or you recompute with `avoid` if one is blocked
     by an incident)
  3. POST trips/                     -> persists ONE of those candidates as
                                         a Trip, which is immediately ACTIVE
  4. (optional, repeatable) POST telemetry/positions/  while the trip is ACTIVE
  5. PATCH trips/{id}/  { "status": "TERMINE" or "ANNULE", ... }
  6. (only if TERMINE) POST trips/{id}/rate/

Two rules that aren't obvious from the shape alone, stated up front because
they'll save you a debugging session:

  A. The "route" object you send to step 3 MUST be exactly one of the
     objects step 1 gave you, unmodified. Every field in it is required
     (not optional) — see "ROUTE CANDIDATE OBJECT" below. Don't
     hand-construct it.

  B. Turn-by-turn text (instruction / voice_instruction / street_name) is
     generated by Valhalla with language=fr-FR, hardcoded server-side. That
     is NOT affected by the rest of this API being in English — those three
     fields will be French regardless. If you want this in English, ask —
     it's a one-line change (language param to ClientValhalla) but it's a
     product call (the app targets Cameroon), not something to change
     silently.

------------------------------------------------------------
1. POST routes/calculate/                 (tag: Routes)
Not persisted — call this as many times as you want, nothing is written to
the database. Cached server-side for 3 minutes per (origin, destination,
avoid, user's routing preferences) combination, so re-calling with the same
inputs is cheap.

Body:
  {
    "origin_lat": 4.0483, "origin_lon": 9.7043,
    "destination_lat": 4.0469, "destination_lon": 9.6970,
    "avoid": [                          // optional, default []
      { "lat": 4.0505, "lon": 9.7021 }  // e.g. an incident's position
    ]
  }

`avoid` is a REAL exclusion sent to Valhalla (exclude_locations) — it is not
a client-side reclassification. Verified end-to-end this session: the same
origin/destination with one incident-sized point in `avoid` changed the
recommended route's distance from 1280m to 1787m with a genuinely different
geometry. This is what "propose a new route near an incident" actually is —
recompute with avoid=[{incident.lat, incident.lon}], don't try to filter the
existing candidates client-side.

Success 200 — a JSON ARRAY (not wrapped in an object) of 1–3 route
candidates, first one is `is_recommended: true` unless traffic pushed
another one up... actually no: is_recommended is always true on index 0 and
false elsewhere, it does NOT reorder based on traffic — see "traffic_level"
notes below. Each item:

  {
    "route_id": "a1b2c3d4e5f6a7b8",     // NOT a database id — see note below
    "label": "Itineraire recommande",   // or "Itineraire 2", "Itineraire 3"
    "distance": 1280,                   // meters
    "duration": 108,                    // seconds, free-flow (no traffic)
    "duration_with_traffic": null,      // seconds, or null — see TRAFFIC below
    "traffic_level": "NORMAL",          // "NORMAL" | "MODERE" | "DENSE" (French values, not translated — see ENUM VALUES note)
    "geometry": "_zavFmyhoQ}LZq]...",   // single encoded polyline, precision 6
    "is_recommended": true,
    "degraded": false,                  // true = Valhalla was down, this is a straight-line fallback, NOT a real route
    "maneuvers": [
      {
        "type": "3",                    // Valhalla's raw maneuver type code, stringified int — NOT mapped to a friendly enum, see note
        "instruction": "Conduisez vers le nord.",       // FRENCH, see header note B
        "voice_instruction": "Continuez pendant 100 metres.",  // FRENCH
        "distance": 100,                 // meters
        "duration": 10,                  // seconds
        "street_name": "Avenue Kennedy"  // FRENCH-locale street naming from OSM/Valhalla, may be blank ""
      }
    ]
  }

Errors:
  400  field-keyed, e.g. { "origin_lat": ["A valid number is required."] }
  401  not authenticated

Notes:
  - `route_id` is a content hash (sha1 of geometry+index, first 16 hex
    chars), computed fresh every call. It is NOT stable across calls with
    different avoid/preferences — don't use it as a persistent identifier
    for anything, it only exists to let you tell the 3 candidates in ONE
    response apart, and to round-trip into POST trips/.
  - "How many candidates you get" depends entirely on the road network
    between the two points — Valhalla only returns a second/third option if
    a genuinely different path exists. Don't assume 3; handle 1.
  - `degraded: true` happens when Valhalla itself is unreachable (circuit
    breaker open after repeated failures) — you get a straight-line
    haversine "route" so the UI has *something*, but do not draw it as a
    road-following path or use its maneuvers (there are none). Show this
    state distinctly to the user (e.g. "routing service degraded").

TRAFFIC (traffic_level / duration_with_traffic) — be aware this is honest
but currently uninformative: the traffic pipeline (P5) exists and is wired
in, but needs weeks of real driver GPS data to produce a real signal. Right
now, with an empty or near-empty EchantillonVitesse table, expect
traffic_level: "NORMAL" and duration_with_traffic: null on essentially every
route. This is not a bug — see the backend team if you want the mechanics
(recent-observed-speed vs typical-speed-for-this-day/hour, compared per
road segment). Don't build UI that assumes these fields are populated yet;
do build UI that displays them when present, because they will start
meaning something once there's usage.

------------------------------------------------------------
2. POST trips/                            (tag: Trips)
Persists a Trip from one of the candidates you got from routes/calculate/.
Starts it immediately — see STATUS LIFECYCLE below, there is no "draft"
state you'll ever observe.

Body:
  {
    "origin_label": "Marche Central",
    "origin_lat": 4.0483, "origin_lon": 9.7043,
    "destination_label": "Hopital General",
    "destination_lat": 4.0469, "destination_lon": 9.6970,
    "destination_place": "a3e6a697-...",  // optional — a Place id from
                                           // GET places/search/ or places/{id}/,
                                           // if the destination came from a
                                           // place lookup rather than a raw
                                           // pin drop. Omit/null otherwise.
    "route": { ...one full candidate object from routes/calculate/, verbatim... }
  }

⚠ Every field inside "route" is required (route_id, label, distance,
duration, duration_with_traffic [nullable but must be present],
traffic_level, geometry, is_recommended, maneuvers, degraded). Take the
exact object you received, don't strip fields you think you don't need —
the request will 400 on the first missing one.

Success 201: a TRIP OBJECT (see below).

Errors:
  400  field-keyed, including nested "route": {"distance": [...]} if the
       route object is malformed
  401  not authenticated

Notes:
  - Only the ONE chosen candidate gets persisted — the other 1–2 candidates
    from routes/calculate/ are gone the moment you don't submit them. If you
    want to let the user switch to a different candidate after creating the
    trip, that's a new trip (or ask backend to support editing — not
    supported today).
  - `degraded` on the submitted candidate is accepted but NOT stored — once
    persisted, there is no way to tell from GET trips/{id}/ afterward
    whether the trip was created from a degraded fallback route or a real
    one. If you need that, keep it client-side (e.g. a local flag) or ask
    backend to add the column.
  - Nothing stops a user from creating a second ACTIVE trip while one is
    already ACTIVE — the backend does not check for this. If your product
    only wants one active trip at a time, enforce that client-side (e.g.
    disable "start trip" while you already have an ACTIVE one from
    GET trips/).
  - `destination_place` accepts any Place id, not just approved ones —
    there's no server-side check that it's StatutLieu.APPROUVE.

------------------------------------------------------------
3. GET trips/                             (tag: Trips)
Query param: ?period=week|month|all  (default: all)

Success 200:
  {
    "results": [ ...TRIP OBJECTs, newest first (by started_at)... ],
    "truncated_at": "2026-07-25T00:00:00Z" | null
  }

`truncated_at` is non-null only when your PLAN's retention limit cut the
results short — i.e. it fires even if you asked for period=all. Current
plan limits: GRATUITE = 30 days, PREMIUM = 365 days (from GET users/me/ ->
plan_limits.history_retention_days — always trust that field over this doc,
it can change). `period` and the plan's retention are combined with
whichever is MORE restrictive; the response never returns older trips than
the plan allows even if you don't pass period at all.

Errors:
  400  { "detail": "period must be 'week', 'month' or 'all'." }  (invalid period value)
  401  not authenticated

------------------------------------------------------------
4. GET trips/{id}/                        (tag: Trips)
Success 200: a TRIP OBJECT.
Errors:
  401  not authenticated
  404  { "detail": "No Trajet matches the given query." }  (not found, OR
       belongs to another user — same response either way, on purpose:
       never confirm that another user's trip id exists)

------------------------------------------------------------
5. PATCH trips/{id}/                      (tag: Trips)
Partial update. All fields optional, send only what changed.

Body (any subset):
  {
    "status": "TERMINE",       // or "ANNULE" — see STATUS LIFECYCLE
    "actual_distance": 1350,   // meters — YOU compute this, see note below
    "actual_duration": 620,    // seconds — YOU compute this, see note below
    "incidents_avoided": 1     // YOU count this, see note below
  }

Success 200: the updated TRIP OBJECT.
Errors:
  400  { "detail": "ACTIF -> ACTIF n'est pas une transition autorisee." }
       (illegal status transition — message text is the model's own,
       currently still French regardless of the fr->en pass done elsewhere;
       flag if you want it translated too)
  400  field-keyed for bad values (e.g. status not in the enum)
  401  not authenticated
  404  not found / not yours

⚠ IMPORTANT — KNOWN BACKEND BEHAVIOR, WORTH DESIGNING AROUND:
If you send status + metrics in the SAME request and the status transition
is illegal, the metrics (actual_distance/actual_duration/incidents_avoided)
ARE STILL SAVED before the 400 is returned — the transition is checked
LAST. Concretely: PATCH {status: "ACTIF", actual_distance: 500} on an
already-TERMINE trip will persist actual_distance=500 and then respond 400.
This is a real bug in the current code (metrics should be atomic with the
transition, not applied unconditionally) — I can fix it if you want, but
flagging it now so you don't get surprised by a trip whose numbers changed
despite getting an error response. Safe pattern until it's fixed: don't
batch a metrics update with a status change you're not certain is legal;
or just retry the metrics-only PATCH separately if a combined one 400s.

STATUS LIFECYCLE (Trip.status):
  PLANIFIE -> ACTIF -> { TERMINE | ANNULE }
  TERMINE and ANNULE are terminal (no further transitions, including back
  to ACTIF).

  You will never see status="PLANIFIE" from the API — POST trips/ creates
  the row and immediately transitions it to ACTIF server-side (fixes
  started_at) before returning the 201. In practice the only transitions
  YOU will ever PATCH are ACTIF -> TERMINE and ACTIF -> ANNULE.

  Enum values are the French model choices, not translated (see ENUM VALUES
  note at the end) — send exactly "PLANIFIE" | "ACTIF" | "TERMINE" | "ANNULE".

actual_distance / actual_duration are NOT computed by the backend from your
telemetry positions — nothing in the pipeline links POST telemetry/positions/
back to a trip's actual_distance/actual_duration. If you want these
populated, YOU track distance/duration client-side (e.g. summing GPS deltas
while ACTIF) and PATCH them in when you complete the trip. Same for
incidents_avoided — nothing increments it automatically when you call
routes/calculate/ with a non-empty avoid; if you want it to mean something,
count client-side how many times you rerouted around an incident during
this trip and PATCH the final count on completion.

------------------------------------------------------------
6. POST trips/{id}/rate/                  (tag: Trips)
Only works once the trip is TERMINE.

Body:
  { "rating": 5, "comment": "Parfait" }   // rating 1-5 required, comment optional (default "")

Success 200: the updated TRIP OBJECT (rating/comment reflected).
Errors:
  400  { "detail": "Only a completed trip can be rated." }  (status != TERMINE)
  400  { "rating": ["Ensure this value is less than or equal to 5."] }  (out of range)
  401  not authenticated
  404  not found / not yours

Note: there is no "already rated" guard — calling this again on the same
trip just overwrites rating/comment. Decide client-side whether to allow
re-rating in your UI.

------------------------------------------------------------
7. DELETE trips/{id}/                     (tag: Trips)
Success 204: empty body.
Errors:
  401  not authenticated
  404  not found / not yours

No restriction on status — you can delete an ACTIVE trip. There's no
"are you sure" server-side; that's a client-side UX decision.

------------------------------------------------------------
8. POST telemetry/positions/              (tag: Telemetry)
Fire-and-forget GPS ingestion while a trip is ACTIVE. This is the P5
traffic pipeline's input — see the TRAFFIC note under routes/calculate/ for
why it doesn't produce visible results yet. Wiring this now is still worth
doing (it's what will eventually make traffic_level/duration_with_traffic
real), but don't expect it to change anything observable today.

Body:
  {
    "trip": "<trip id, must be YOUR trip and currently ACTIF>",
    "positions": [
      {
        "lat": 4.0483, "lon": 9.7043,
        "speed_kmh": 32.5,      // optional
        "heading": 180,         // optional, 0-359
        "timestamp": "2026-01-01T10:00:00Z"   // required, ISO 8601
      }
      // up to 500 positions per call
    ]
  }

Success 202: empty body. ALWAYS 202 on success, even if the batch is
silently dropped (see mode_invisible below) — this is intentional, the
client should never need to distinguish "accepted and processed" from
"accepted and silently discarded" since positions are never persisted
either way (privacy commitment — raw positions live only in a short-lived
Redis stream, never written to Postgres; only 5-minute aggregates are).

Errors:
  400  { "trip": ["Invalid pk \"...\" - object does not exist."] }
       — this fires for THREE different real situations, all indistinguishable
       in the response on purpose (never confirm which):
         1. the trip id doesn't exist at all
         2. the trip belongs to another user
         3. the trip exists and is yours but is NOT status=ACTIF (e.g.
            you're still sending positions after you PATCHed it to TERMINE)
  400  { "positions": ["Maximum 500 positions per batch."] }
  400  { "positions": ["This list may not be empty."] }
  401  not authenticated

Silent suppression: if the authenticated user has mode_invisible=true
(GET users/me/ -> invisible_mode), this endpoint returns 202 immediately
and publishes NOTHING — no error, no indication to the client. This is
deliberate (privacy setting), not a bug — don't build retry logic around a
202 that "didn't seem to work," there's nothing to retry.

TRIP OBJECT (full shape, as returned by create/list/detail/update/rate):
{
  "id": "<uuid>",
  "origin_label": "Marche Central",
  "origin_lat": 4.0483, "origin_lon": 9.7043,
  "destination_label": "Hopital General",
  "destination_lat": 4.0469, "destination_lon": 9.6970,
  "destination_place": "<uuid>" | null,
  "chosen_route_id": "a1b2c3d4e5f6a7b8",   // == routes[0].route_id, redundant but both present
  "planned_distance": 1280,     // meters, from the route candidate at creation time
  "planned_duration": 108,      // seconds, ditto
  "actual_distance": 1350 | null,   // null until YOU patch it (see note above)
  "actual_duration": 620 | null,    // ditto
  "status": "ACTIF" | "TERMINE" | "ANNULE",  // never "PLANIFIE" in practice
  "incidents_avoided": 0,       // starts at 0, only changes if YOU patch it
  "rating": 1-5 | null,
  "comment": "..." | null,
  "started_at": "<ISO 8601>",   // set the instant the trip is created
  "ended_at": "<ISO 8601>" | null,   // set the instant status becomes TERMINE (NOT set for ANNULE)
  "routes": [ ...exactly ONE persisted route, see ROUTE OBJECT (PERSISTED) below... ]
}
All fields are read-only from the client's perspective except via the
specific write endpoints above (PATCH for status/actual_*/incidents_avoided,
rate/ for rating/comment) — this GET/list shape never accepts input.

ROUTE OBJECT (PERSISTED) — the single entry inside trips[].routes, NOT the
same shape guarantees as a routes/calculate/ candidate:
{
  "route_id": "a1b2c3d4e5f6a7b8",
  "is_recommended": true,          // ALWAYS true here — the persisted route
                                    // is always marked recommended regardless
                                    // of what you submitted, since it's the
                                    // only one that exists post-creation
  "label": "Itineraire recommande",
  "distance": 1280, "duration": 108,
  "duration_with_traffic": null,
  "traffic_level": "NORMAL",
  "geometry": "_zavFmyhoQ...",
  "maneuvers": [ { "order": 0, "type": "3", "instruction": "...", "voice_instruction": "...", "distance": 100, "duration": 10, "street_name": "..." }, ... ]
}
Note: NO "degraded" field here (see the note under POST trips/ above) —
that flag is lost on persistence.

ERROR-SHAPE RULES (same as the rest of the API, repeated here for
completeness — see AUTH_API_FRONTEND.txt for the general rules):
- Field-keyed validation errors: { "<field_name>": ["message", ...] }
- Business-rule errors (bad state transition, rate on non-terminated trip,
  invalid period, quota-style checks) that this module's OWN code raises:
  { "detail": "message" } — and these ARE in English (this module was
  translated this session).
- Errors that come from DJANGO/DRF ITSELF rather than this module's code
  (default 404 "No X matches the given query", "Invalid pk ... - object
  does not exist", "This field is required.", numeric range validators,
  etc.) are ALSO now in English as of this session (LANGUAGE_CODE was fixed
  from fr-fr to en-us — this was a real gap found while writing this doc:
  before the fix, these framework-level messages were still French even
  though this module's own custom messages were English). If you see a
  French message anywhere going forward, it's either a bug (report it) or
  Valhalla-generated navigation text (see header note B), not a translation
  gap in our own code paths.

ENUM VALUES — worth restating clearly: field NAMES and free-text error
messages were translated to English this session; the actual VALUES of
Django-model-backed choice fields were NOT (would require a database
migration, out of scope). So you will see, and must send back verbatim:
  status: "PLANIFIE" | "ACTIF" | "TERMINE" | "ANNULE"
  traffic_level: "NORMAL" | "MODERE" | "DENSE"
Same rule applies to the auth module's plan ("GRATUITE"/"PREMIUM") and
vehicle_type ("VOITURE" etc.) — see AUTH_API_FRONTEND.txt.

WORKED EXAMPLE — the exact flow, verified against the live server this
session (real request/response pairs, values may differ slightly by run):

1) POST routes/calculate/
   { "origin_lat": 4.0483, "origin_lon": 9.7043,
     "destination_lat": 4.0469, "destination_lon": 9.6970, "avoid": [] }
   -> 3 candidates, recommended distance 1280m

2) User picks candidate[0]. POST trips/ with that exact object under "route"
   -> 201, trip status "ACTIF", planned_distance 1280

3) (while driving) POST telemetry/positions/ every ~10-30s with the trip id
   -> 202 each time, nothing visible yet (see TRAFFIC note)

4) An incident appears on the route (from community module — see a
   separate doc for incidents/, or ask). You recompute:
   POST routes/calculate/ with the SAME origin/destination but
   avoid=[{ "lat": <incident.lat>, "lon": <incident.lon> }]
   -> recommended distance jumps to 1787m with a different geometry —
   this is a genuinely different route, confirmed working end-to-end.
   (Whether you create a NEW trip for this or just re-route the existing
   ACTIVE one client-side is a product decision — the backend has no
   "reroute an existing trip" endpoint; POST trips/ always creates a new row.)

5) Trip finishes. PATCH trips/{id}/
   { "status": "TERMINE", "actual_distance": 1820, "actual_duration": 145 }
   -> 200, status TERMINE, ended_at set

6) POST trips/{id}/rate/  { "rating": 4, "comment": "Un peu plus long que prevu" }
   -> 200, rating/comment reflected
