  GET /api/config/                        (public, sans jeton)
    { "cities": [...], "vehicle_types": {"VOITURE": "Voiture", ...},
      "incident_types": {"DANGER": "Danger", ...},
      "minimum_app_version": "x.y.z" }
    -> plus besoin de coder ces listes en dur.

  POST   /api/devices/                    enregistrer / mettre a jour un appareil
    { "push_token", "platform", "app_version", "os_version", "language"? }
  DELETE /api/devices/{id}/               desenregistrer (a la deconnexion)
    L'enregistrement fonctionne ; l'ENVOI des notifications n'existe toujours
    pas (voir 4) -- garder l'ecran Notifications grise.

  POST /api/routes/calculate/  — etapes intermediaires
    "waypoints": [ {"lat": ..., "lon": ...}, ... ]   dans l'ordre de passage.
    Chaque manoeuvre porte "stop_index" : l'index (0-based) de l'etape
    atteinte quand elle termine un troncon intermediaire, sinon null.
    (Le constat du 11/09 "waypoints ignore" n'est plus vrai.)

  GET /api/incidents/nearby/  — deux modes en plus des cellules H3
    lat + lon (+ radius_km, defaut 10, max 20)

    -> leve la limite des "trois anneaux" en vue large : utiliser la bbox de
       l'ecran. Le mode cells reste le plus rapide (cache par cellule) pour
       l'appel repete en conduite.

  Signalements en temps reel (WebSocket)
    wss://easyway-api.easy-transact.net/ws/incidents/
    Protocole complet : REALTIME_INCIDENTS_FRONTEND.txt.

2. NOUVEAU — zones de vitesse le long du trajet (section 6)

  POST /api/speed-zones/along-route/      (authentifie)
    { "geometry": "<polyline6 de routes/calculate>", "buffer_m": 30 }
    buffer_m optionnel, defaut 30, max 100.

  Reponse, triee par start_m :
    [ { "id": "...", "name": "Akwa", "speed_limit_kmh": 50,
        "start_m": 1109, "end_m": 3328 }, ... ]
    start_m / end_m : metres depuis le debut du trajet, le long du trajet.

  Usage :
    - un appel au depart et a chaque recalcul d'itineraire ;
    - remplace le sondage de /api/speed-limit/ tous les 250 m (plus de
      retard en sortie de zone) ;
    - des zones peuvent se chevaucher : la plus restrictive couvrant la
      distance parcourue gagne (meme regle que /api/speed-limit/) ;
    - hors de toute zone : limite deduite du road_class, comme aujourd'hui.
  /api/speed-limit/ reste disponible (hors trajet, ou en secours).

5. NOUVEAU — lieux sur la carte et pendant la navigation (16/10/2026)

Lieux renvoyes : lieux APPROUVES proposes par les utilisateurs ou ajoutes par
EasyWay (back-office), + etablissements (HOPITAL, GARAGE...) marques
"visible sur la carte". Les lieux importes d'OpenStreetMap restent dans la
recherche seulement (trop nombreux pour la carte).
Chaque point :
  { "id", "kind": "place"|"establishment", "name", "category",
    "category_label", "address", "neighborhood", "city", "lat", "lon" }
  kind=place -> fiche : GET /api/places/{id}/

  GET /api/places/map/?min_lat=&min_lon=&max_lat=&max_lon=&categories=a,b
    Carte d'accueil : rectangle visible (cote <= 50 km, meme regle que
    incidents/nearby en mode bbox). A rappeler quand la carte bouge
    (avec un petit delai, ~300 ms). Reponse { "results": [...], "truncated": bool }
    -- au plus 300 points ; truncated=true -> inviter a zoomer.

  POST /api/places/along-route/
    { "geometry": "<routes/calculate -> geometry (polyline6)>",
      "buffer_m": 100 (10..500, optionnel), "categories": ["HOPITAL", ...] (optionnel) }
    Pendant la navigation : meme usage que speed-zones/along-route (un appel
    au depart et a chaque recalcul d'itineraire). Chaque point porte en plus
      "position_m" : metres depuis le debut du trajet (tri croissant)
      "distance_m" : ecart au trace
    -> afficher les prochains lieux et annoncer "Station Tradex dans 2 km"
       (position_m - distance deja parcourue).

  GET /api/places/map/categories/
    [ { "category", "label", "count", "kind" } ]  -- pour les filtres de la carte.

6. NOUVEAU — meilleur itineraire en cours de route (19/10/2026)

Pendant la navigation, le serveur peut proposer une route plus rapide quand
un bouchon se forme (vitesses mesurees des conducteurs EasyWay + embouteillages
signales, deja pris en compte par le calcul d'itineraire).

  POST /api/trips/{id}/better-route/      (trajet ACTIF de l'appelant)
    { "lat", "lon", "heading"?, "remaining_waypoints"?: [{lat, lon}, ...] }
    -> toutes les 1-2 min pendant la navigation (limite : 120 appels/heure).
    { "reason": "BETTER_FOUND" | "NO_BETTER" | "NO_ALTERNATIVE" | "OFF_ROUTE" | "NO_ROUTE",
      "better_route": <meme forme qu'un element de routes/calculate> | null,
      "current_duration_s", "new_duration_s", "time_saved_s" }
    BETTER_FOUND : proposer "Itineraire plus rapide : -7 min via ..." (label),
      le conducteur accepte ou ignore -- jamais de changement automatique.
      Seuil : au moins 2 min ET 10 % du temps restant gagnes.
    OFF_ROUTE : le conducteur a quitte sa route -> recalcul classique via
      routes/calculate (comme aujourd'hui).

  POST /api/trips/{id}/switch-route/      (le conducteur accepte)
    { "lat", "lon", "route": <better_route tel quel> }   -> 200 Trip
    Le trace garde la partie deja parcourue + la nouvelle route. Ensuite :
    guider sur route.maneuvers et redemander speed-zones/along-route et
    places/along-route avec la nouvelle geometry.

7. NOUVEAU — itineraires voiture / moto alourdis par les signalements (20/10/2026)

  POST /api/routes/calculate/  -- deux champs facultatifs en plus :
    "vehicle_type": "VOITURE"|"MOTO"|"TAXI"|"CAMION"|"BUS"|"UTILITAIRE"
        (defaut : le vehicule du profil ; le conducteur peut en changer pour ce trajet)
    "vehicle_id": "<uuid de users/me/vehicles/>"  -- vehicule d'agence : son type prime.
  Moteur de calcul : moto -> "motorcycle" (pistes et rues etroites acceptees,
  ignore le trafic en direct mesure sur les voitures) ; voiture/taxi -> "auto" ;
  camion/utilitaire -> "truck" ; bus -> "bus".

  Chaque itineraire renvoye porte en plus :
    "vehicle_type": "MOTO",
    "delay_from_reports": 390,          // secondes ajoutees par les signalements
    "reports_applied": [ { "id", "type", "subtype", "delay", "applied_as": "delay" } ]
  "duration_with_traffic" inclut ce retard : c'est la duree a afficher.
  L'ordre de la liste et "is_recommended" suivent cette duree finale (a moins
  d'1 min d'ecart : le moins de signalements, puis le plus court).
  -> afficher "+6 min a cause de 2 signalements".

  Regles cote serveur :
    - un signalement compte s'il est a moins de 30 m du trace, dans le meme sens
      (cap a moins de 45 deg), pondere par sa fiabilite (votes) et son age ;
    - POLICE et RADAR : aucun effet (pas de detour pour eviter un controle) ;
    - route barree / inondation confirmee (2e auteur ou confirmation) : la route
      est evitee ; non confirmee : simple ralentissement. Inondation : evitee par
      une moto des le premier signalement ;
    - moto : 30 a 50 % du retard voiture selon le type (remonte les files).

  Renvoyer l'itineraire choisi tel quel a POST /api/trips/ (les champs ajoutes
  sont acceptes). Le type de vehicule est garde sur le trajet et reutilise par
  better-route (seuil desormais : 2 min ET 10 %).


8. CORRIGE — boucle / demi-tour au depart d'un itineraire (26/10/2026)

  POST /api/routes/calculate/ : nouveau champ optionnel
    origin_speed_kmh (float, km/h) : vitesse GPS au moment du calcul.

  Pourquoi : origin_heading oblige le calcul a partir dans cette direction.
  A l'arret, le cap GPS du telephone est faux -> l'itineraire partait parfois
  dans le mauvais sens puis faisait demi-tour (ex. Deido -> Bafoussam).

  Regles cote serveur :
    - origin_speed_kmh < 10 : origin_heading est ignore ;
    - origin_speed_kmh >= 10 : origin_heading est respecte ;
    - origin_speed_kmh absent : le serveur calcule aussi sans cap et garde ce
      resultat s'il est plus rapide d'au moins 2 min.

  A faire cote appli : envoyer origin_speed_kmh avec origin_heading, ou ne pas
  envoyer origin_heading quand la vitesse GPS est proche de 0.


9. NOUVEAU — noter un garage (27/10/2026)

  Seuls les garages se notent : lieu de categorie garage/mecanique (ex.
  "Garage / mecanique") ou etablissement de type GARAGE. Note 1 a 5 +
  commentaire facultatif (500 caracteres max). Un seul avis par utilisateur et
  par garage : renvoyer une note la remplace. Aucun point gagne.

  Reperer un garage : nouveaux champs dans places/map, places/along-route et
  GET /api/places/{id}/ :
    "is_garage": true, "rating_average": 4.2 | null, "rating_count": 12

  GET /api/garages/{id}/reviews/?page=1          (public ; {id} = id du lieu
                                                   ou de l'etablissement)
    { "garage": {id, kind, name}, "average": 4.2 | null, "count": 12,
      "my_review": {id, rating, comment, status, ...} | null,   (si connecte)
      "count"/"next"/"previous"/"results": [
        {id, rating, comment, author_name | null, created_at, updated_at} ] }
    author_name est null si l'auteur est en mode invisible.

  POST /api/garages/{id}/reviews/                 (connecte)
    { "rating": 1-5, "comment": "..." }
    -> 201 (premier avis) ou 200 (modification) : l'avis + average/count/my_review
    Limite : 10 avis par heure. 404 si {id} n'est pas un garage.

  DELETE /api/garages/{id}/reviews/mine/          -> 204

  Un avis peut etre retire par la moderation : il sort de la moyenne ; son
  auteur le voit encore dans my_review avec status "RETIRE". Le modifier le
  republie.
